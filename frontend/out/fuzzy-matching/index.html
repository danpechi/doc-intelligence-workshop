Semantic Matching

ai_similarity · vector_search()

Exact string matching breaks down in the real world — merchant names get abbreviated, customer queries use informal language, failure descriptions vary by technician. ai_similarity scores semantic closeness between any two text strings, enabling fuzzy matching directly in SQL.

Industry: 🏦 Financial Services | Matching: Match raw transaction merchant names against a canonical merchant registry, even when abbreviated, misspelled, or truncated.

ai_similarity(text1, text2)

Returns: DOUBLE between 0.0 and 1.0

Best for: Scoring known candidate pairs. Use with CROSS JOIN + ROW_NUMBER() for best-match selection.

Use when: Catalog size < 10,000 entries

vector_search(index, query, ...)

Returns: Top-K matching rows with similarity scores

Best for: Finding matches from a large catalog without a CROSS JOIN. Millisecond latency at any scale.

Use when: Catalog size > 10,000 entries

1

Score pairwise similarity with ai_similarity

Use a CROSS JOIN to generate all candidate pairs, then score each with ai_similarity. This is perfect for small catalogs (hundreds to low thousands of entries).

Pairwise similarity scoringsql
-- Score every (transaction, merchant) pair
SELECT
    t.transaction_id,
    t.merchant_name_raw,
    c.canonical_name,
    c.category,
    ROUND(ai_similarity(t.merchant_name_raw, c.canonical_name), 3) AS similarity_score
FROM merchant_transactions t
CROSS JOIN merchant_canonical c
WHERE t.transaction_id IN ('TXN00001', 'TXN00002', 'TXN00003')
ORDER BY t.transaction_id, similarity_score DESC;
ℹ️

Score interpretation

  • 0.9 – 1.0: Near-identical or same entity with minor formatting differences
  • 0.7 – 0.9: Strong semantic match — likely the same concept
  • 0.5 – 0.7: Related but distinct — review manually
  • Below 0.5: Semantically dissimilar
2

Select the best match per record

Use ROW_NUMBER() OVER (PARTITION BY ... ORDER BY similarity DESC) to pick the top-1 match per source record.

Best-match selection with window functionssql
-- Best-match: top-1 canonical merchant per transaction
WITH scored AS (
    SELECT
        t.transaction_id,
        t.merchant_name_raw,
        t.amount,
        c.merchant_id,
        c.canonical_name,
        c.category,
        ai_similarity(t.merchant_name_raw, c.canonical_name) AS sim_score,
        ROW_NUMBER() OVER (
            PARTITION BY t.transaction_id
            ORDER BY ai_similarity(t.merchant_name_raw, c.canonical_name) DESC
        ) AS rnk
    FROM merchant_transactions t
    CROSS JOIN merchant_canonical c
    LIMIT 1000  -- limit cross join for demo
)
SELECT
    transaction_id,
    merchant_name_raw,
    amount,
    canonical_name   AS matched_merchant,
    category,
    ROUND(sim_score, 3) AS confidence
FROM scored
WHERE rnk = 1
ORDER BY confidence DESC
LIMIT 30;
3

Validate matches with ai_query as a judge

Add a validation layer: use the LLM to confirm whether the top similarity match is actually correct, providing explainability and a quality gate beyond the raw score.

LLM-as-judge validationsql
-- Validate top matches with ai_query as a judge
WITH top_matches AS (
    SELECT
        t.transaction_id, t.merchant_name_raw, c.canonical_name, c.category,
        ROW_NUMBER() OVER (PARTITION BY t.transaction_id ORDER BY ai_similarity(t.merchant_name_raw, c.canonical_name) DESC) AS rnk
    FROM merchant_transactions t CROSS JOIN merchant_canonical c LIMIT 500
)
SELECT
    transaction_id, merchant_name_raw, canonical_name, category,
    from_json(ai_query(
        'databricks-meta-llama-3-3-70b-instruct',
        CONCAT('Does "', merchant_name_raw, '" refer to the merchant "', canonical_name, '"? Answer YES or NO.'),
        responseFormat => '{"type":"json_schema","json_schema":{"name":"response","schema":{"type":"object","properties":{"match_confirmed":{"type":"boolean"},"confidence":{"type":"string"},"reason":{"type":"string"}}}}}'
    ), 'match_confirmed BOOLEAN, confidence STRING, reason STRING') AS validation
FROM top_matches
WHERE rnk = 1
LIMIT 10;

The summarize-embed-validate pattern

For large catalogs, the full production pattern is:
1. Summarize catalog entries with ai_query to improve embedding quality
2. Embed using a Vector Search Delta Sync index (auto-updated)
3. Retrieve top-K matches with vector_search()
4. Validate top match with ai_query as a judge
4

Generate semantic summaries for better embeddings

Before embedding, generate a concise 2-3 sentence summary. This dramatically improves retrieval quality because the embedding captures semantic meaning rather than formatting artifacts.

Summarize catalog entries before embeddingsql
-- Step 1: generate summaries (store in a new column)
ALTER TABLE canonical_name
ADD COLUMN IF NOT EXISTS semantic_summary STRING;

UPDATE main.ai_functions_workshop_fins.merchant_transactions
SET semantic_summary = ai_query(
    'databricks-meta-llama-3-3-70b-instruct',
    CONCAT('Write a 2-sentence plain-language description of this record that captures its key meaning: ', merchant_name_raw)
)
WHERE semantic_summary IS NULL;

-- Step 2: the Vector Search Delta Sync index picks up the new column automatically

vector_search() — scale to millions of entries

ℹ️

Prerequisites

A Vector Search endpoint and Delta Sync index must be created first. See the Databricks documentation or use the databricks-vector-search skill to set them up.
Semantic retrieval with vector_search()sql
-- After creating a Vector Search index on the catalog table:
SELECT
    source.*,
    vs.score
FROM (
    SELECT explode(result) AS vs_result
    FROM vector_search(
        index    => 'main.ai_functions_workshop_fins.merchant_transactions_index',
        query    => 'Your query text here',
        num_results => 5
    )
) vs_raw
LATERAL VIEW json_tuple(to_json(vs_result), 'merchant_name_raw', '_score') AS text_val, score
JOIN main.ai_functions_workshop_fins.merchant_transactions source ON source.merchant_name_raw = text_val
ORDER BY score DESC;
